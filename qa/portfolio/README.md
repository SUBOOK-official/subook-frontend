# 수북 QA 프로젝트 포트폴리오

> **가상 QA 수행 시나리오** — 수북의 실제 서비스와 정책을 바탕으로, QA가 초기 기획부터 참여한 6주 프로젝트를 구성했다. 이 문서 묶음의 일정·역할·발견 및 수정 이력·수행 상태는 설정이다. 실행 가능한 Selenium·Postman·JMeter 코드와 현재 실행 증거는 [자동화 실행 가이드](../stack/README.md)에서 별도로 제공한다.

## 프로젝트 개요

수북은 판매자가 맡긴 수능 교재를 수거·검수하고 구매자에게 판매한 뒤 판매자에게 정산하는 중개 서비스다. QA는 상품을 고르는 화면만으로 검증 범위를 제한하지 않았다. 동일 교재의 개별 재고, 카드 인증과 주문 생성의 순서, 부분환불, 과거 수거 건의 수수료 정책까지 하나의 거래 흐름으로 다뤘다.

| 항목 | 프로젝트 설정 |
|---|---|
| 기간 | W1~W6, 기획 검토부터 RC2 출시 판정까지 |
| 역할 | QA 담당 1명, FE·BE·운영 담당과 협업 |
| 대상 | 구매자·판매자 통합 웹, 관리자 업무, public-web 서버 API |
| 핵심 도구 | Selenium WebDriver JavaScript, Postman Collection/Newman, Apache JMeter |
| 산출물 | 테스트 전략, 업무 TC 40건, 결함 8건, 주간 기록, 회귀 자동화, 릴리스 보고서 |
| 자동화 구조 | 화면 Page Object + 독립 세션 / 요청별 API fixture / JMeter 혼합 부하 |
| 테스트 데이터 | 합성 회원·교재·연락처, 정책 전후 수거, 재고 0·1·2, 가격 경계값 |

## 수행 흐름

| 주차 | 업무와 판단 | 산출물·완료 조건 |
|---|---|---|
| W1 요구사항 검토 | 판매·구매·운영 상태 흐름을 작성했다. '결제창 닫기'를 정상 구매만큼 중요한 시나리오로 분리했다. 수수료 변경이 기존 수거에 소급되는지 질문하고 수거별 스냅샷 유지로 기대 결과를 확정했다. | 상태 전이·정책 질문 목록, P0 위험 목록 |
| W2 테스트 설계 | 동일 옵션이 여러 개별 교재로 구성되는 점을 테스트 데이터에 반영했다. 재고0·1·2, 업로드15MiB±1, 무료배송50000±1, 수수료10000 경계를 선정했다. | TC 40건, 테스트 데이터 사전, 진입·종료 기준 |
| W3 기능 검증 | 상품·장바구니·주문서의 수량과 식별자를 비교했다. 수량 초과와 교재 ID 중복을 티켓으로 등록하고 수정 건을 별도 재검증했다. | SIM-BUG-001·002, Selenium 구매 회귀 |
| W4 결제·인증 검증 | 결제 중단, 중복 복귀, 서명 변조, 재고 충돌, 승인 후 확정 실패를 분리했다. 회원 조회 무응답도 장애 주입으로 확인했다. | SIM-BUG-003·004·005, 결제·인증 API 회귀 |
| W5 판매·운영·부하 검증 | 수거별 요율과 정산 보류 조건을 확인했다. B2B 재시도 참조번호를 비교하고, JMeter로 정상 문의·인증 거절·결제 중단 요청을 섞어 부하를 구성했다. | SIM-BUG-006·007·008, JMeter 계획·결과 분석 |
| W6 회귀·출시 판정 | 수정 영향 영역과 P0 전체를 재검증했다. 기능 차단이 없는 용량 표기 개선만 후속 릴리스로 이관했다. | RC2 결과 39 Pass / 1 Deferred, 조건부 출시 승인 |

## 테스트 전략

**P0**는 잘못된 청구·재고 판매·정산·권한 노출을 막는 테스트다. 하나라도 실패하거나 실행이 막히면 출시를 중단한다. **P1**은 정상 거래와 주요 복구 흐름, **P2**는 사용성·호환성, **P3**는 기능이 유지되는 표시 개선이다. TC 우선순위와 결함 심각도는 별도 필드로 관리했다.

| 기법 | 수북 적용 | 확인 대상 |
|---|---|---|
| 경계값 분석 | 재고2권에서 3회 선택, 49999·50000·50001원, 15MiB±1byte | 초과·일치 조건의 오프바이원 오류 |
| 동등 분할 | 인증/미인증, 정상/품절/숨김, 동의/미동의 | 상태별 허용 경로 |
| 상태 전이 | 인증 전 세션 → 주문 생성 → PG승인 → 주문 확정 | 순서 오류와 중단 후 잔존 상태 |
| 결정표 | PG승인·DB확정·PG취소 각각 성공/실패 | 보상 처리와 운영 경보 |
| 오류 주입 | RPC무응답, 503 후 복구, 연속 실패 | 시간 제한·재시도·사용자 안내 |
| 위험 기반 회귀 | 결제 변경 시 중단·중복·재고·환불 재검증 | 변경 영향 누락 방지 |

### 진입 기준

- 검증 빌드와 정책 기준이 고정되고, 이전 빌드와 변경점이 공유되어야 한다.
- 합성 회원·교재·수거·주문 데이터를 초기화할 수 있어야 한다.
- PG·알림·DB를 실제 연동하는 테스트와 fixture 테스트의 대상이 구분되어야 한다.
- P0 시나리오에 필요한 데이터나 접근 권한이 없으면 Blocked로 기록한다.

### 종료 기준

- P0 전부 통과, 미종결 S1·S2 0건, Blocked 0건.
- 실패한 TC는 수정 빌드에서 다시 실행하고 관련 회귀도 통과해야 한다.
- Deferred는 영향·우회 방법·후속 담당 역할·재검증 조건을 기록한다.
- 부하 판정에는 요청 수, 측정 구간, 워밍업, 오류율, p95와 측정 범위를 함께 적는다.

## 도구 선택과 담당 업무

Selenium은 수북 웹의 반복 구매·인증 흐름에 적용했다. Page Object에 화면 선택자를 모으고, 임의 sleep 대신 표시·활성화·URL 조건을 기다렸다. 테스트마다 새 Chrome 세션과 장바구니를 사용하고 성공·실패 화면을 모두 남겼다. 480px 검증은 모바일 웹 레이아웃 검증으로 정의했다.

Postman은 정상 응답뿐 아니라 오류 코드, 추가 호출 유무, 보상 호출 순서를 검증하는 데 사용했다. Collection을 Newman으로 실행하고 JSON·JUnit 결과를 남겼다. 예를 들어 '이미 결제 완료' 응답에는 PG 재승인이 없어야 하며, 자동취소까지 실패하면 주문 해제 대신 운영 경보가 있어야 한다.

JMeter는 1·10·25명의 가상 사용자, ramp-up, 요청 간격, 혼합 비율을 설정했다. API 오류 응답이 기대 결과인 경우 HTTP 401·303 자체를 실패로 세지 않고 assertion으로 판정했다. 워밍업을 제외한 측정과 전체 dashboard를 구분했다.

공고의 Appium·UIAutomator는 네이티브 앱 자동화 확장 시 선택할 도구로 남겼다. 이 포트폴리오의 구현 범위는 수북 웹과 서버 API다.
