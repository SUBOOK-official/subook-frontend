## W3 일일 업무 기록

구매 흐름 검증 중 재고 상한과 개별 교재 ID 매핑에서 결함2건을 등록했다. 두 건 모두 주문 직전 재작업을 유발하므로 P1으로 분류했다. QA-BUG-002는 최초 수정 후 삭제·재선택에서 다시 발생해 Reopened로 전환했다. 다음 회차는 장바구니 표시 수량뿐 아니라 요청 book_id와 주문서 품목을 함께 비교한다.

## W4 결함 분류 회의 기록

- QA-BUG-004는 결제 중단만으로 재고가 묶이므로 S1/P0, 출시 차단으로 합의했다.
- 카드 승인 성공만을 정상 결과로 보지 않고 DB확정 실패와 자동취소 실패도 결제 결정표에 추가했다.
- QA-BUG-005는 인증 상태를 임의로 성공 처리하지 않고 제한 시간 후 복구하도록 요구했다.
- 수정 검증은 실패 TC만 반복하지 않고 정상 결제·중복 복귀·미인증 회원까지 포함했다.

## W5 테스트 진행 현황

첫 실행 결과를 누적한 기준으로 40건 중28 Pass,8 Fail,4 Blocked였다. Blocked4건은 관리자 역할 데이터, 부분환불 데이터, 환불 보류 주문, 정산 월 경계 데이터 준비 문제였다. 데이터 준비 완료 후 원래 기대 결과를 바꾸지 않고 다시 실행했다.

부하 모델은 합성 정상 문의50%, 토큰 없는 계정 연결25%, 카드 인증 중단25%로 구성했다. 1·10·25 VU를 순차 실행하고 요청 간격100ms를 적용했다. 응답 코드만 확인하면 유효한 401·303이 오류로 집계되므로 응답 계약 assertion으로 판정했다.

결함8건 중7건을 재검증 후 종결했고, QA-BUG-008 한 건은 Deferred로 남겼다. P0 결함2건은 모두 Closed이며 TC-030을 제외한 모든 업무 TC가 Pass다. 재실행 횟수를 신규 TC 수로 합산하지 않았고 Deferred를 Pass로 바꾸지 않았다.

## 회고

초기 TC에는 정상 구매가 중심이었으나 중단·중복·보상 실패를 추가하면서 결제 검증 범위가 명확해졌다. 옵션명과 수량만 비교하던 화면 검증에는 개별 교재 식별자 검증을 추가했다. 결함 종결은 개발자의 수정 완료 통보가 아니라 원 재현 경로와 영향 범위의 재검증을 기준으로 했다.

다음 프로젝트에서는 요구사항 단계에서 상태 전이와 금액 경계를 먼저 합의하고, 실패를 만들기 쉬운 로컬 fixture와 실제 DB·PG 통합 검증을 함께 계획한다.
